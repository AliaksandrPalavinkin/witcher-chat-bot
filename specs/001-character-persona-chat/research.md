# Phase 0 Research: Witcher Character Persona Chat

## 1. Calling Groq's Llama models from Spring Boot

**Decision**: Use LangChain4j's `OpenAiChatModel` (module `langchain4j-open-ai`), configured with `baseUrl("https://api.groq.com/openai/v1")`, the Groq API key, and the chat model name set to a current Groq-hosted Llama chat model (e.g., `llama-3.3-70b-versatile`, confirmed against Groq's current model list at integration time since availability changes). Exposed to the rest of the app behind a plain `ChatLanguageModel` bean.

**Rationale**: Groq exposes an OpenAI Chat Completions-compatible REST API, and LangChain4j's OpenAI client works unmodified against any OpenAI-compatible base URL — no custom HTTP client needed. LangChain4j is the chosen framework for this project (per explicit decision), and it gives prompt templating, `AiServices`, and the same `EmbeddingStoreContentRetriever`/RAG building blocks used for the lore pipeline, keeping the whole LLM stack on one framework instead of mixing two.

**Alternatives considered**:
- Raw `WebClient` calls straight to Groq's REST endpoint — more control over request/response shape, but reimplements what LangChain4j's OpenAI client already provides (retries, message formatting, streaming) for no real benefit here.
- Spring AI's OpenAI-compatible `ChatModel` — also a viable abstraction and arguably more idiomatic inside a Spring Boot app, but superseded by the explicit choice to standardize on LangChain4j for this feature.

## 2. Lore retrieval (RAG) storage

**Decision**: PostgreSQL with the `pgvector` extension, accessed through LangChain4j's `PgVectorEmbeddingStore` (module `langchain4j-pgvector`), running locally (e.g., via Docker for dev) since the project has no persistence configured yet.

**Rationale**: Matches the explicit requirement to use pgvector; LangChain4j's `PgVectorEmbeddingStore` handles schema creation and similarity search directly, and plugs straight into LangChain4j's `EmbeddingStoreContentRetriever` for RAG, keeping ingestion/retrieval code small; pgvector is free/self-hosted, consistent with the "fully free" constraint.

**Alternatives considered**:
- LangChain4j's in-memory `InMemoryEmbeddingStore` — zero infra, but loses all embeddings on restart and doesn't scale to a growing book/game-dialogue corpus; rejected because the corpus is expected to grow (books now, game dialogue later).
- Managed vector DBs (Pinecone, Weaviate Cloud, etc.) — add a paid/external dependency that conflicts with the "fully free" constraint and self-hosted preference implied by using pgvector.

## 3. Embedding model for lore chunks

**Decision**: LangChain4j's local `AllMiniLmL6V2EmbeddingModel` (module `langchain4j-embeddings-all-minilm-l6-v2`, ONNX runtime, runs in-process, no external API call or key).

**Rationale**: Groq's public API is chat-completion focused and is not being used here for embeddings; a locally-run embedding model keeps the whole pipeline free with no second API key/rate limit to manage, and LangChain4j ships this integration out of the box, matching the chosen framework.

**Alternatives considered**:
- OpenAI embeddings API (via LangChain4j's `langchain4j-open-ai`) — reliable and high quality, but introduces a paid, rate-limited dependency purely for embeddings, which conflicts with the "fully free" goal.
- Cohere free-tier embeddings — another external account/API key and its own rate limits, not clearly better than a local model for this scale.

## 4. Lore ingestion pipeline

**Decision**: A startup/CLI ingestion component that reads plain-text book files placed under `src/main/resources/lore-corpus/` (supplied locally by the project owner — copyrighted book text is not fetched or generated by tooling), splits them with LangChain4j's `DocumentSplitters.recursive(...)` (chunk size tuned for retrieval quality, with overlap), and feeds them through LangChain4j's `EmbeddingStoreIngestor` (embedding model + `PgVectorEmbeddingStore` wired in) to produce and store the vectors. Ingestion is idempotent/re-runnable (skip or replace already-ingested documents, tracked via `metadata.source`) so it can be re-run when new corpus files (e.g., future game dialogue) are added.

**Rationale**: Standard RAG ingestion pattern; reuses LangChain4j's splitter/ingestor utilities instead of hand-rolled chunking/embedding code; keeps the corpus source-controlled outside the repo (or gitignored) since book text is copyrighted material the user supplies themselves.

**Alternatives considered**:
- Manual SQL inserts of pre-computed vectors — no reuse of LangChain4j's splitter/ingestor pipeline, error-prone, harder to extend to new corpora.
- A separate external ETL tool/service — unnecessary operational overhead at this scale (one user, a handful of books).

## 5. Handling Groq free-tier limits and failures

**Decision**: Wrap Groq calls with a bounded retry (short backoff, small retry count) for transient errors, and on persistent failure/rate-limit, return a persona-appropriate in-character fallback line (e.g., Geralt grumbling that he's "not in the mood to talk right now") rather than surfacing a raw error — satisfying FR-010's "indicate in-character when unsure" and keeping the experience from breaking immersion.

**Rationale**: Free-tier LLM APIs commonly have strict requests-per-minute/day limits; a single-user hobby app should degrade gracefully instead of leaking HTTP/API errors to the user.

**Alternatives considered**:
- Let errors propagate as generic HTTP 5xx — simplest to implement but breaks the persona illusion and gives a poor UX for something explicitly meant to feel like talking to a character.
- Queue and retry indefinitely — unnecessary complexity for a single-user, synchronous chat UX; conflicts with the 10s response-time goal (SC-001).

## 6. Conversation/session state

**Decision**: This service holds no conversation state at all. Each persona endpoint is a pure request/response call: the caller optionally supplies a `conversationContext` string (a recent-history excerpt or summary) in the request body, which is folded into the prompt for that one call and then discarded. Nothing is written to memory or storage as a result of a request.

**Rationale**: Per explicit design decision, persona routing, per-user session tracking, and conversation-history summarization (last ~10-15 messages) are all owned by a separate, external AI gateway service. Keeping this backend stateless avoids duplicating that responsibility and keeps each persona endpoint trivially horizontally scalable / restart-safe, since there is no in-memory state to lose.

**Alternatives considered**:
- In-memory conversation store scoped to this service (the earlier single-endpoint design's approach) — rejected once the architecture moved to independent per-persona endpoints with an external gateway; keeping state here would duplicate/conflict with the gateway's own session tracking.
- Persisting conversation history to a database here — unnecessary and out of scope; the gateway is the single owner of cross-call conversation state.

## 7. Client interface for v1

**Decision**: Expose two persona-specific REST endpoints, `POST /api/v1/geralt/chat` and `POST /api/v1/jaskier/chat`, each accepting/returning JSON (see `contracts/chat-api.md`). No dedicated web frontend is built as part of this feature, and no generic "current persona" endpoint exists — the caller (an external gateway) picks which endpoint to call. This service is not intended to be called directly by an end-user's browser.

**Rationale**: The explicit design is one independent endpoint per persona rather than a single endpoint with a persona-switch mechanism, so that each persona can carry its own request path, system prompt, and generation parameters (temperature) cleanly, and so a separate gateway can own routing/caching without this service needing any "which persona is active" concept.

**Alternatives considered**:
- A single `/api/chat` endpoint with a persona selector field or session-based active persona — the earlier design; rejected in favor of fully independent endpoints per persona, which better isolates each persona's distinct temperature/creative-license configuration and matches the intended gateway-in-front architecture.
- Building a full web UI (HTML/JS chat widget) now — not requested by the spec and out of scope; the direct caller of this API is the gateway, not an end-user UI.

## 8. Per-persona generation parameters (temperature)

**Decision**: Configure two separate LangChain4j `OpenAiChatModel` beans (or equivalent named beans), one per persona, identical in model/base-URL/API-key but differing in `temperature` (and any other sampling parameters that matter): a low temperature for Geralt (favors deterministic, lore-grounded answers) and a higher temperature for Jaskier (favors varied, creative output). Each persona's controller/service uses only its own bean.

**Rationale**: The spec (FR-006) requires Jaskier to be able to improvise original creative content while Geralt stays strictly grounded — this is a generation-parameter difference, not just a system-prompt difference, so it has to be modeled as distinct model configurations rather than one shared client with a runtime-swapped prompt.

**Alternatives considered**:
- One shared `ChatLanguageModel` bean with temperature passed per-call — LangChain4j's high-level `ChatLanguageModel` abstraction does not uniformly support per-call parameter overrides across providers as cleanly as configuring distinct model instances; two named beans is simpler and keeps each persona's configuration self-contained and easy to reason about independently.
